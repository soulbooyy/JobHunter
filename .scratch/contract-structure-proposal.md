## 2. Catalog conventions

The recommendation is **27 planned documents in a flat `docs/contracts/` directory**, with stable, descriptive section locators inside each document. This count is a reviewable proposal, not a permanent constraint, service count, package tree, or all-at-once writing obligation. For example, `execution-runtime.md :: Durable effects and recovery` denotes a proposed section, not an existing anchor.

Each entry below defines ownership, exclusions, consuming references, source families, and later-detail ownership. Section 4 supplies the consumer-specific scope for every Slice; section 3 provides the family map. Together those mappings define each document's prospective consumers. Common interpretation lives once; business content, command semantics, and eligibility remain with their owners. References convey meaning, not permission to mutate another domain.

All documents consume applicable `common.md` conventions and `storage.md` obligations only where relevant. That shorthand does not require all future common/storage sections to be completed. Later detailed Grill covers representations and acceptance examples within the bounded topics identified here; this proposal supplies none of them.

## 7. Five structural decisions for this round

These are new proposed organizational choices, not old Q/S decisions. The complete catalog and matrices above are their reviewable recommendation; unchanged entries remain proposed until the user responds. The five choices can be discussed independently because all alternatives preserve the same already-accepted business boundaries.

1. **Dedicated shared Save protocol document:** recommend candidate-save as the single Application commit-protocol owner; alternative is one clearly owned section within resumes-grounding, with Profile/Evidence/import/Advisor referencing it. This changes location, not fact ownership or transaction scope.
2. **Fit documentation granularity:** recommend one fit-analysis document with separate Candidate, Resume, assessment/scoring and orchestration scopes; alternative is separate task documents plus one common assessment/scoring/orchestration owner. Either arrangement must let one Fit proceed without completing the other.
3. **Shared platform safety location:** recommend platform-safety separate from collection; alternative is a independently referenceable safety section in a combined source-access document. Executor never requires Collector success, and safety never grants execution approval.
4. **Runtime and recovery location:** recommend execution-runtime owns the execution/recovery protocol once, alongside separate budget/storage/tools; alternative is a separate recovery document with a precisely narrowed protocol owner and explicit reference from runtime. Avoid duplicate invocation/fencing lifecycle definitions; platform work consumes only the relevant shared scope.
5. **Delivery granularity:** recommend asking W6 to promote the SL-02/07/10 pairs above to separate delivery Slices with the explicit original-to-proposed correspondence, keeping SL-03 a protected vertical capability with internal implementation milestones.
