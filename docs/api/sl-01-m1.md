## 1. What the frontend can use

M1 maintains independent mutable manual application entries: company name, role title and a user-provided application URL. The entry view is entered through a Job Pool button and remains separate from formal Jobs/Companies. An entry is not a Job or JobVersion and supplies no JD, analysis, fit, preparation, application status or application-history capability. See MAE-001 and WSP-005.

Workspace initialization happens at backend startup. There is no Workspace HTTP resource, workspace ID, create/switch-workspace API or frontend initialization command. A failed backend startup must not be rendered as a successful empty entry list. Only a successful list response with `items: []` establishes the empty state.

| UI action | Method and path | Success result |
| --- | --- | --- |
| Create | `POST /api/v1/manual-application-entries` | Entry ID only |
| Load all entries | `GET /api/v1/manual-application-entries` | `{items: [...]}` |
| Read saved detail | `GET /api/v1/manual-application-entries/{manual_application_entry_id}` | Complete entry |
| Save complete edit | `PUT /api/v1/manual-application-entries/{manual_application_entry_id}` | Complete saved entry |
| Delete | `POST /api/v1/manual-application-entries/{manual_application_entry_id}/delete` | Deleted entry ID only |
| Resolve saved URL for explicit opening | `POST /api/v1/manual-application-entries/{manual_application_entry_id}/resolve-url` | `{application_url: "..."}` |

All six successes are **HTTP 200**, including create and delete. There is no `data`/`success` wrapper, `201` create or `204` business-delete response. Commands require a JSON object and `Content-Type: application/json`; all declared fields are required and non-null. Unknown/system fields are rejected. The path ID is never repeated in the body. GET requests have no body or query options. No pagination, search, filtering, custom sort, PATCH, batch commands or receipt lookup API exists. MAE-015 owns this interface.

## 2. Local connection and OpenAPI

Default backend origin: `http://127.0.0.1:8765`. Generated OpenAPI: `GET /openapi.json` on that origin. Interactive Swagger/ReDoc pages are disabled. OpenAPI describes transport types; the linked Contracts additionally control validation, concurrency, recovery and browser effects.

The default allowed Host is exactly `127.0.0.1:8765`. Browser Origin access is disabled until explicitly configured; this also matters for browser requests whose Origin happens to equal the backend origin. Requests without Origin may pass the validated Host boundary. No login/token flow is introduced. `localhost` and `127.0.0.1` are different configured aliases; do not infer either from headers. WSP-006 owns these restrictions.

For a future UI served at **the explicitly selected example origin** `http://localhost:5173`, start the backend from the repository root:

```sh
JOBHUNTER_ALLOWED_ORIGINS=http://localhost:5173 \
  uv run --locked python -m jobhunter.main
```

This example admits that frontend origin while the API remains at `http://127.0.0.1:8765`; it does not select or create a frontend toolchain. To call the API as `http://localhost:8765`, also explicitly configure `JOBHUNTER_ALLOWED_HOSTS=127.0.0.1:8765,localhost:8765`. A future proxy must preserve an admitted Host and Origin or use explicitly configured values; no proxy is currently provided.

An allowed cross-origin preflight receives HTTP 204, permits `GET, POST, PUT` and the `Content-Type` request header, and uses the exact allowed Origin rather than a wildcard. Do not add custom authorization/idempotency headers: `request_id` is a create-body field. Unapproved Host/Origin returns `403 ACCESS_DENIED` before business handling. Browser CORS enforcement can hide a rejected response from JavaScript, so a fetch failure alone does not establish a business error code or rollback.

For isolated integration data, use an existing empty temporary directory through `JOBHUNTER_DATA_DIRECTORY`; see the backend README. Do not use real user data for design fixtures.

## 3. Complete entry and form fields

A detail or update response contains exactly seven fields (MAE-002):

```json
{
  "manual_application_entry_id": "8f395bc2-5dc4-4b9a-8d31-a9e9056072f1",
  "company_name": "Acme",
  "role_title": "Frontend Engineer",
  "application_url": "https://example.test/apply?q=one%20two#step",
  "revision": 1,
  "created_at": "2026-09-19T10:00:00.000Z",
  "updated_at": "2026-09-19T10:00:00.000Z"
}
```

| Field | Wire type / constraints | UI use |
| --- | --- | --- |
| `manual_application_entry_id` | Lowercase, hyphenated UUIDv4 string | Stable row/detail key; read-only |
| `company_name` | Scalar Unicode string; 1–200 code points after fixed outer trim; one line | Editable company field |
| `role_title` | Same text rules as company | Editable role field |
| `application_url` | Scalar Unicode string; 1–8192 code points after trim; valid absolute HTTP(S) URL | Editable destination field; preserve admitted spelling |
| `revision` | JSON integer-valued number, `1..9007199254740991` | Saved optimistic-concurrency token; send for update/delete/resolve |
| `created_at` | UTC timestamp `YYYY-MM-DDTHH:mm:ss.sssZ` | Read-only creation time |
| `updated_at` | Same timestamp format | Read-only last actual change time; list ordering |

The editable form has only three business fields. Do not submit timestamps, an entry ID, `workspace_id`, `status`, `schema_version`, JD, click count or last-opened time. `request_id` belongs only to create, not to an entry or an edit form.

### Validation details that affect UI controls

COM-025–031 and MAE-003/004 govern validation. Client validators and input widgets must preserve them:

- Length counts Unicode code points, not UTF-16 code units, graphemes or UTF-8 bytes. A supplementary character counts as one. Reject unpaired surrogates.
- Use the fixed outer-whitespace set in [COM-026](../contracts/common.md#com-026), not a language's default `trim()`. Outer U+0085 is removed; U+FEFF is preserved. Preserve internal spacing, case and Unicode representation.
- Company/role reject remaining controls and line/paragraph separators. Missing is `REQUIRED`; null is `INVALID_TYPE`; empty after trim is `BLANK_VALUE`. Do not truncate oversized text.
- URL scheme comparison is case-insensitive; an explicit `http://` or `https://` authority delimiter and a valid nonempty host are required. No credentials/userinfo, remaining whitespace/controls, backslashes or malformed `%` escapes. Explicit ports are nonempty ASCII decimal in `0..65535`.
- Unicode host/path, localhost and IP destinations are allowed. `HTTP://Example.test:80/./apply` is saved in that exact admitted spelling. Do not normalize/punycode/rewrite it or prepend a guessed scheme. `http://127.1/`, `https:////example.test`, `https://example.test:/` and `https://u:p@example.test/` are invalid.
- No DNS, page-availability check or target fetch occurs. A saved URL is not evidence that the destination exists or accepts applications.
- UUIDs reject uppercase, surrounding whitespace and other UUID versions instead of repairing them.
- Revision is numeric: `1`, `1.0`, `1e0` are equivalent. Strings, booleans, null and fractional numbers are rejected; `1.0000000000000001` must not round into validity. Usually the UI simply returns the exact revision received from the server.

Generated input schemas use `x-post-trim-maxLength` and descriptions for trimmed-text limits. Applying a raw `maxLength: 200` before trim would reject some legal padded input. OpenAPI and fixtures are derived aids; they do not replace the full Contract rules or certify a frontend validator.

## 4. Endpoint examples and result semantics

All examples use the base `/api/v1/manual-application-entries`; `{id}` below is the `manual_application_entry_id` shown above. Example IDs and timestamps are illustrative. Retain the real values returned by the backend.

### Create — `POST` base

```json
{
  "request_id": "3d38577b-0a57-47c8-a3c1-ae787c4580f2",
  "company_name": "Acme",
  "role_title": "Frontend Engineer",
  "application_url": "https://example.test/apply?q=one%20two#step"
}
```

HTTP 200:

```json
{"manual_application_entry_id": "8f395bc2-5dc4-4b9a-8d31-a9e9056072f1"}
```

Read detail or refresh the list to obtain the saved record. Creation starts at revision 1 with equal timestamps. The frontend generates a new UUIDv4 `request_id` for each distinct intentional creation and retains the submitted request while its outcome is unresolved. MAE-005/007/008 govern replay:

| Reuse of an admitted request ID | Result |
| --- | --- |
| Same admitted content; original still exists | HTTP 200, same original entry ID; no new row or edit |
| Same admitted content; original was edited | Same original ID; read its current content separately |
| Different admitted content | `409 REQUEST_CONFLICT` |
| Same admitted content; original was deleted | `409 ORIGINAL_ENTRY_DELETED`; no recreation |
| Concurrent identical requests | One original identity and receipt |
| New request ID with equal content | New independent entry; content is not deduplicated |

Validation precedes replay lookup. Invalid content does not become valid because the request ID already exists. Fingerprints and receipts are server internals; clients neither submit them nor receive a receipt resource. Do not silently generate a new request ID to recover an uncertain creation.

### List — `GET` base

HTTP 200 has one field, `items`, containing complete seven-field entries from section 3:

```json
{
  "items": [
    {
      "manual_application_entry_id": "8f395bc2-5dc4-4b9a-8d31-a9e9056072f1",
      "company_name": "Acme",
      "role_title": "Frontend Engineer",
      "application_url": "https://example.test/apply?q=one%20two#step",
      "revision": 1,
      "created_at": "2026-09-19T10:00:00.000Z",
      "updated_at": "2026-09-19T10:00:00.000Z"
    }
  ]
}
```

Empty success is `{"items": []}`. The list includes every current entry, sorted by `updated_at` descending and ID lexicographically ascending on ties. It has no total-count, cursor or page fields. Do not send query options. MAE-009.

### Detail — `GET /{id}`

No body. HTTP 200 returns the complete entry in section 3; absent targets return `404 NOT_FOUND`. A read is an observation, not a lease against later edits/deletion.

### Update — `PUT /{id}`

```json
{
  "revision": 1,
  "company_name": "Acme",
  "role_title": "Senior Frontend Engineer",
  "application_url": "https://example.test/apply?q=one%20two#step"
}
```

HTTP 200 returns the complete saved entry, including its authoritative revision and timestamps. For the example's actual content change, revision becomes 2, `created_at` stays unchanged, and `updated_at` is the maximum of current UTC millisecond time and its previous value. Timestamps can tie; never infer revision from them.

All three business fields are required on every save. Validation comes first, then existence, then expected revision, then content comparison. A stale equal-content save still returns `REVISION_CONFLICT`. With a matching revision, equal post-trim content is a no-op and returns the unchanged record. At maximum revision a no-op still succeeds, but an actual change returns `REVISION_EXHAUSTED`. The backend does not merge fields or recreate a missing row. MAE-006/010/017.

### Delete — `POST /{id}/delete`

```json
{"revision": 2}
```

HTTP 200:

```json
{"manual_application_entry_id": "8f395bc2-5dc4-4b9a-8d31-a9e9056072f1"}
```

Use the currently observed revision, not necessarily the example's 2. The business row is physically removed, with no recycle bin or restore endpoint. The create receipt survives. A repeated completed delete returns `NOT_FOUND`; a stale revision on an existing row returns `REVISION_CONFLICT`. Deliberate re-addition is a new create with a new request ID. MAE-011.

### Resolve URL — `POST /{id}/resolve-url`

For an existing record at revision 2:

```json
{"revision": 2}
```

HTTP 200:

```json
{"application_url": "https://example.test/apply?q=one%20two#step"}
```

This endpoint is used **before deletion**, independently of the preceding delete example. It returns the saved URL only after checking existence and revision in one observation. Missing/stale returns `NOT_FOUND`/`REVISION_CONFLICT`. It does not open a browser, fetch a target, follow redirects, record a click or mutate the entry. A subsequent edit/deletion does not recall the resolved URL. UI navigation must not fall back to cached or unsaved text if resolution fails. MAE-012.

## 5. Errors and UI recovery

Every owned error has exactly `code`, `message`, `field_errors`. For example, HTTP 422:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed.",
  "field_errors": [{"field": "role_title", "code": "REQUIRED"}]
}
```

Map behavior/localized text from codes, never parse `message`. A field error has only `field` and `code`; `$` means whole-document or unknown-field error without echoing the submitted key. Field-error order is not meaningful. Non-field-specific errors have `field_errors: []`. Error bodies do not contain the latest record or current revision; use a read when recovery calls for one. COM-029/030; MAE-016.

| HTTP / code | Where / meaning | Frontend handling |
| --- | --- | --- |
| 400 `BAD_REQUEST` | Malformed JSON/transport or non-JSON command | Correct the request; preserve editor input |
| 403 `ACCESS_DENIED` | Host/Origin not admitted | Fix local integration configuration; business command was not executed |
| 422 `VALIDATION_ERROR` | Field/path/query admission | Show field/global issues; preserve input |
| 404 `NOT_FOUND` | Detail/update/delete/resolve target missing | Explain that the saved entry is unavailable; do not recreate automatically |
| 409 `REVISION_CONFLICT` | Update/delete/resolve expected revision is stale | Read current state; preserve dirty input; no automatic resubmit with new revision |
| 409 `REQUEST_CONFLICT` | Create request ID reused with different admitted content | Explain the request conflict; no silent fresh-key retry |
| 409 `ORIGINAL_ENTRY_DELETED` | Matching create replay after deletion | Explain that the original is deleted; no automatic resurrection |
| 409 `REVISION_EXHAUSTED` | Changed update at maximum revision | Report rejection; no-op remains valid |
| 503 `STORAGE_UNAVAILABLE` | Storage failure; mutation non-commit confirmed | Report failed save/delete; preserve input and saved state |
| 503 `OUTCOME_UNKNOWN` | Mutation outcome needs verification | Do not claim failure/rollback or automatically replay |
| 500 `INTERNAL_ERROR` | Unexpected failure | An ambiguous write response requires verification, not an assumption of rollback |

Field codes: `REQUIRED`, `UNKNOWN_FIELD`, `INVALID_TYPE`, `BLANK_VALUE`, `TOO_LONG`, `INVALID_CHARACTERS`, `INVALID_FORMAT`, `OUT_OF_RANGE`. Missing and explicit null are distinct. See [COM-030](../contracts/common.md#com-030) for precise meanings.

Timeout, connection loss and unrecognized/malformed responses can occur after a commit. MAE-014 requires the following distinction:

| Situation | Recovery obligation |
| --- | --- |
| Uncertain create | Keep exact submitted request/content in current-page memory; explicit verify/retry reuses that request ID/content; success then reads current saved state |
| Uncertain update/delete | Read current state; do not automatically replay a command at a fresh revision |
| Dirty editor during refetch | Keep unsaved input separate; refetch does not silently replace it |
| Page state lost after refresh/browser restart | Prompt list inspection; no persistent pending-command queue or automatic recreation |
| Valid Contract 4xx on a replay | Current operation is rejected; it does not prove an earlier creation never committed |

`OUTCOME_UNKNOWN`, loading, dirty input and verification-needed presentation are transient UI concerns, not persisted entry statuses. Do not invent an entry `status` field. No automatic background command retry or per-field autosave is part of M1.

## 6. Interaction states to account for in UI design

These are frontend obligations derived from WSP-005 and MAE-013/014/017, not claims of an implemented UI or a prescribed visual layout.

| Interaction | States or distinctions the UI needs to represent |
| --- | --- |
| Entry list | Loading, successful empty list, populated saved list, read/backend-unavailable error |
| Create/edit | Dirty form, submitting, field/global rejection, confirmed saved result, stale revision, uncertain outcome requiring verification |
| Delete | Pending action, confirmed deletion, missing/stale target, definite failure versus uncertain result |
| Open destination | Waiting browsing context, resolving current ID/revision, resolution failure, blocked/closed context, navigation initiated |

Opening begins with an explicit user click that requests a neutral waiting browsing context through user activation. When that context is available, resolve the saved ID/revision; navigate it only after successful resolution. On failure it closes or displays failure. If blocked/closed, report the observable handoff failure without automatically creating another context; a new click rechecks the entry.

Before external content gains control, it must have no usable opener and receive no referrer information. Creating a waiting page or receiving a resolve response alone is not navigation success. Success text can indicate that navigation was initiated, never that the external page loaded or an application was submitted. Do not infer a particular popup-blocker cause from a null handle alone. This requires later real-browser verification; API tests do not prove it. MAE-013 owns the complete browser requirement.
