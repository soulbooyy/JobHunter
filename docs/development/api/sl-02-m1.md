# Independent Resume and Portrait API

## Current backend integration — 2026-09-24.S2M1S1-r2

The schema-7 backend implements the deterministic source and Entry-scoped portrait-planning stages of the revised SL-02.M1 authority. It provides independent ResumeVersion schema 2 documents, stable logical entry/block IDs, atomic Save/default transitions, deterministic Evidence projection, mode-aware rebuild state, immutable incremental plans and zero-call reuse/reattachment completion. The generated `/openapi.json` is the transport reference for public routes. The planner/completion boundary is internal and introduces no public operation. The frontend now consumes this public surface directly; the earlier Profile/Evidence write routes and legacy request shapes are absent from generated client code and UI navigation.

Normative semantics remain owned by [Resume](../../contracts/candidate/resumes-grounding.md#res-017), [Evidence](../../contracts/candidate/evidence.md#evd-016), [Profile](../../contracts/candidate/profile.md#pro-010), [Candidate Save](../../contracts/candidate/candidate-save.md#sav-018), [Common](../../contracts/common.md#com-050), [Workspace](../../contracts/foundation/workspace.md#wsp-013) and [Storage](../../contracts/foundation/storage.md#sto-054). This guide is derived integration help and does not extend those Contracts.

### Available operations

Paths are relative to `/api/v1`. All successful operations return HTTP 200. GET operations accept no body or query. POST bodies are closed UTF-8 JSON objects with identity encoding, no duplicate decoded keys, at most 100,000 nodes and 32 container levels. Resume Create/Save allow 8,388,608 bytes; the other commands allow 65,536 bytes.

| Method and path | Complete command or result |
| --- | --- |
| `GET /resumes` | `{resumes, default_resume_selection}`; ACTIVE roots in creation order |
| `GET /resumes/{resume_id}` | Exact current `{resume,resume_version}`; removed roots remain readable |
| `GET /resumes/versions/{resume_version_id}` | Exact retained ResumeVersion schema 2 |
| `POST /resumes` | Resume Create; returns `CREATED` and the selection snapshot |
| `POST /resumes/{resume_id}/save` | Expected root revision plus complete document; returns `UPDATED` or `UNCHANGED` |
| `POST /resumes/{resume_id}/rename` | Expected root revision and `resume_name`; returns `UPDATED` or `UNCHANGED` |
| `POST /resumes/{resume_id}/remove` | Expected root and selection revisions plus nullable explicit replacement; returns `REMOVED` or `UNCHANGED` |
| `POST /workspace/default-resume/set` | Selection revision and ACTIVE `default_resume_id`; returns `UPDATED` or `UNCHANGED` |
| `GET /workspace/portrait` | Read-only `{state,portrait}` observation; never starts or repairs work |
| `POST /workspace/portrait/refresh` | Exact selection revision and source version; returns `UPDATED` or `UNCHANGED` state |

The six POSTs share one lifetime `request_id` namespace. Admission and canonical fingerprinting precede receipt lookup. A same-key, same-command retry returns the original completion snapshot; a different admitted request conflicts. Preserve the complete original request across transport loss or `OUTCOME_UNKNOWN`. Current equality or a current read cannot prove the earlier command's result.

### Resume document and stable IDs

Create supplies `request_id`, `resume_name` and the complete document. Save replaces `resume_name` with expected root `revision`. The document is:

```json
{
  "contacts": {"full_name": "Ada", "phone_number": null, "email": "ada@example.test"},
  "header_presentation": {"optional_items": []},
  "sections": [{
    "kind": "SKILL",
    "members": [{
      "entry_id": "11111111-1111-4111-8111-111111111111",
      "fields": {"skill_name": "Python"},
      "content": [{
        "type": "PARAGRAPH",
        "block_id": "22222222-2222-4222-8222-222222222222",
        "runs": [{"text": "Built durable services", "marks": []}]
      }]
    }]
  }],
  "document_presentation": {
    "font_family": "SOURCE_HAN_SANS",
    "font_size_pt": 12,
    "line_spacing_pt": 14,
    "theme_color": "#333333"
  }
}
```

Each entry owns kind-specific `fields` and local content. Paragraphs and every ordered/unordered list item carry a `block_id`. IDs are UUIDv4 and unique across the document. Reordering, editing, block-type conversion and restoring retained draft/history content may preserve an ID owned by that Resume. Copying an ID across Resumes or assigning it to another owner returns `INVALID_REFERENCE` at the supplied identity field. New copied or newly created logical content needs a fresh ID.

The first Resume atomically becomes default and advances selection revision. Removing a non-default Resume submits `replacement_resume_id:null`. Removing the default supplies the exact observed replacement, except that removing the final Resume is legal with null replacement and clears selection. The server never chooses a replacement. A non-default Save does not affect portrait source; a default Save or default switch updates source independently of eventual portrait success.

### Deterministic Evidence and portrait state

Every created ResumeVersion has one stored canonical Evidence projection with `schema_version:1` and extraction key `resume.v1`. Source order is document order. Entry Evidence IDs are `entry/<entry_id>`; block Evidence IDs are `block/<entry_id>/<block_id>`. The backend saves exact canonical UTF-8 bytes, rederives them from the retained ResumeVersion on read and rejects mismatches as corruption. Reads do not create projections.

`GET /workspace/portrait` returns `CurrentPortraitState` plus a Portrait only when status is `READY`. State statuses are `NO_SOURCE`, `EMPTY_SOURCE`, `QUEUED`, `RUNNING`, `READY` and `FAILED`; the exact nullable `source_resume_version_id`, `build_id`, `portrait_id` and `failure_code` combinations are validated. A source transition obsoletes any older active build and creates an AUTOMATIC queued build. No source yields `NO_SOURCE`; a source with no deterministic Evidence units yields `EMPTY_SOURCE`. Refresh requests FULL work without adding a client mode field. A matching active FULL build deduplicates to `UNCHANGED`; an active AUTOMATIC build is obsoleted and replaced by a new FULL build.

No worker claims queued portrait builds, invokes a model or publishes a model-generated READY/FAILED pair in this delivery. Protected Invocation association, one-request execution, bounded model recovery/publication and semantic quality Eval are the subsequent SL-03.M2 consumer stage. No provider, model, network or renderer call occurs in a Candidate command transaction, and ordinary reads never start remote work.

### Entry-scoped portrait planning foundation

`CandidateProfileProjection.entries` is `ProfileIndexEntry[]`, with each row exactly `{source_entry_id, name, description, evidence_refs}`. All refs belong to that source Entry. The portrait's `generation.kind` admits `MODEL`, `INCREMENTAL` or `REUSE` under PRO-012; exact historical reattachment preserves the immutable pair and its original provenance. Derivation-plan/Entry-diff metadata remains internal and is not a new client command payload.

For AUTOMATIC work, the backend chooses the latest successful compatible portrait from the same Resume by durable success order. An exact compatible target version is reattached with zero model calls. Otherwise it compares logical Entry IDs and admitted semantic fields/content, ignores excluded presentation and hidden-link values, regenerates every dirty Entry, rebinds unchanged groups to the target version and drops removed groups. Deletion-only changes finish as a new `REUSE` pair without a model call. FULL bypasses every reuse path. The target Entry order, generated/reused/removed partition, baseline, rebindings and configuration key are stored once before dispatch and reused unchanged after restart.

Grouped model output is one `entry_results` group per requested dirty Entry. Explicit empty groups remove that Entry's prior Profile rows. Missing, duplicate or unrequested groups and cross-Entry evidence IDs are invalid; accepted groups replace the affected Entry rows and final assembly follows target Entry order. These Domain rules and the zero-call persistence paths are implemented and tested. Actual provider input construction, Invocation execution and model-result publication remain gated on SL-03.M2. Frontend must consume server `source_entry_id` for attribution, never reconstruct cross-Entry capability unions or infer readiness from a reusable baseline. Materials/editor operations do not require a ready portrait.

### Current frontend integration

The frontend generates its Candidate transport types from this live OpenAPI composition. `/resumes`, `/resumes/new` and `/resumes/{id}/edit` use complete schema-2 documents. Contacts and structured entries are edited inside the selected Resume; no independent Profile/Evidence Save, source picker, adoption, diff or baseline control remains. The local preview consumes the same in-memory document and remains an S2-M1 draft view, not a Materials/PDF result.

The TipTap adapter persists only the canonical paragraph/list/run/mark AST and its `entry_id`/`block_id` values. Ordinary text/mark edits, reorder, paragraph/list conversion and undo/redo preserve logical identity; split, merge, paste and duplication follow RES-020. Empty editor placeholders are omitted rather than assigned transport identity. The backend still validates ownership, uniqueness and all canonical limits.

The user-portrait page performs a read-only `GET /workspace/portrait`, displays every server status and preserves `source_entry_id` attribution for each Profile row. Reload never refreshes. The visible “重新生成” action alone sends `POST /workspace/portrait/refresh` with the exact observed selection revision and source version. Because the actual semantic consumer is not connected, real browser integration currently proves NO_SOURCE, EMPTY_SOURCE and QUEUED plus explicit refresh; it does not claim a model-generated READY result. READY/FAILED response combinations and cross-Entry evidence rejection are covered by client response validation.

## Connection and storage

At this historical checkpoint, the binary required schema 5 and schema 3 was the earlier Candidate backend checkpoint. Current schema-7 connection, startup and migration behavior is described above and maintained in [backend/README.md](../../../backend/README.md). The supported launcher remains `uv run --locked python -m jobhunter.main` and owns storage for the entire server lifetime. Never point integration tests at user data.

OpenAPI is served at `/openapi.json` under the same Host/Origin admission. Configure the actual frontend origin explicitly, for example `JOBHUNTER_ALLOWED_ORIGINS=http://127.0.0.1:5173`. An Origin header must match configured origins exactly; configuring only frontend CORS does not admit it on the backend. This API supplies no wildcard, public bind or authentication service. The frontend uses the repository-root `./scripts/dev` launcher and Vite same-origin `/api` proxy; see [frontend operation](../../../frontend/README.md). There is no additional default-selection GET: the Resume list supplies the selection atomically with its roots.

All operations below return 200 on success. POST bodies are complete closed JSON objects. Send `Content-Type: application/json` (optional UTF-8 charset); only identity Content-Encoding is accepted. Queries are prohibited, and GET accepts no body. Duplicate decoded object keys, even nested, are rejected. All POSTs are limited to 100,000 value/container nodes and 32 container levels, enforced before canonicalization. Byte limits are 8,388,608 for Resume Create/Save, 1,048,576 for Evidence Create/Update, and 65,536 for the other five commands.

## Reads

Paths are relative to `/api/v1`. Exact IDs come from server responses. UUIDv4 path values must be canonical lowercase. All current/list observations use one database snapshot. Lists are complete, with no pagination or sort/filter parameters.

| GET path | Result |
| --- | --- |
| `/profile` | `{profile, profile_version}`; mandatory initialized authority, never an absent/lazy state |
| `/profile/versions/{profile_version_id}` | Exact ProfileVersion |
| `/evidence-items` | `{evidence_items: [{evidence_item, current_evidence_item_version_id, fields}]}`; ACTIVE only, ordered by created_at then ID; no full body in this projection |
| `/evidence-items/{evidence_item_id}` | `{evidence_item, evidence_item_version}`; retired roots remain readable |
| `/evidence-items/versions/{evidence_item_version_id}` | `{kind, evidence_item_version}`; kind is projected from its retained Item |
| `/evidence-baselines/current` | Current EvidenceBaselineSnapshot |
| `/evidence-baselines/{evidence_baseline_snapshot_id}` | Exact EvidenceBaselineSnapshot |
| `/resumes` | `{resumes: [Resume], default_resume_selection}`; ACTIVE roots ordered by created_at then ID; default is not pinned/reordered |
| `/resumes/{resume_id}` | `{resume, resume_version}`; removed roots remain readable |
| `/resumes/versions/{resume_version_id}` | Exact ResumeVersion |

Profile roots contain profile_id, current_profile_version_id, revision, created_at and updated_at. Evidence roots additionally have permanent kind and ACTIVE/RETIRED status. Resume roots additionally have resume_name and ACTIVE/REMOVED status. Each Version contains its own ID, owning root ID, schema_version=1, created_at and owned content; it has no business revision, updated_at or is_current. The storage schema number is independent of serialized schema_version.

DefaultResumeSelection is exactly `{default_resume_id: UUID|null, revision: integer}`. A new Workspace has one null ProfileVersion, an empty real Baseline, no Resume, and null selection at revision 1; Preferences remains lazy. Baseline contains its ID, schema_version=1, created_at and members of `{evidence_item_id, evidence_item_version_id}`, sorted by Item ID. It contains no copied facts and is not a Resume field.

## Commands and results

Every body includes a client-generated UUIDv4 `request_id`. Existing target IDs occur only in paths. The table lists all other required fields; nullable fields must still be present. `revision` is the expected mutable root revision, except set-default where it is the selection revision.

| POST path | Other complete body fields | Success payload in addition to request_id/outcome |
| --- | --- | --- |
| `/profile/save` | revision, full_name, phone_number, email | profile, profile_version |
| `/evidence-items` | kind, fields, content | evidence_item, evidence_item_version, evidence_baseline_snapshot_id |
| `/evidence-items/{evidence_item_id}/save` | revision, fields, content | Same Evidence payload |
| `/evidence-items/{evidence_item_id}/retire` | revision | Same Evidence payload |
| `/resumes` | resume_name, profile_version_id, header_presentation, sections, document_presentation | resume, resume_version, default_resume_selection |
| `/resumes/{resume_id}/save` | revision, profile_version_id, header_presentation, sections, document_presentation | resume, resume_version |
| `/resumes/{resume_id}/rename` | revision, resume_name | resume, resume_version |
| `/resumes/{resume_id}/remove` | revision, default_resume_selection: `{revision}`, replacement_resume_id: UUID or null | resume, resume_version, default_resume_selection |
| `/workspace/default-resume/set` | revision, default_resume_id: UUID | default_resume_selection |

Create outcomes are CREATED. Changed content/name/selection returns UPDATED; lifecycle changes return RETIRED or REMOVED. Valid no-ops return UNCHANGED. Replay preserves the original outcome and entire original result, not a REPLAYED flag. Content no-op does not publish a Version, advance time/revision or publish a Baseline. Rename changes only the Resume root. Retirement/removal retains its current Version and history. Each successful command, including no-op, creates a lifetime receipt.

The nine commands share one request_id namespace, separate from Entry and Preferences. Preserve the complete original request and key until its outcome is established. A reused key with different admitted command, path, revision or canonical content conflicts. Field admission occurs before receipt lookup. Evidence Update first validates its envelope, reads the target's immutable kind, then validates that kind's fields; a missing target is 404 even if its key was used elsewhere. No frontend-supplied kind belongs in Update.

On a receipt miss, stale revision fails even when content is equal. New/switched Profile bindings must be current at commit; new/switched Evidence bindings must be current and ACTIVE. An unchanged binding in the preceding formal ResumeVersion may remain historical/retired. Source updates never rewrite Resume content or references. Local Resume edits never write Profile/Evidence. Do not infer that preserved wording is semantically supported by a newly adopted source.

The first Resume Create establishes default selection at revision 2. Concurrent subsequent creates preserve that selection. Set-default uses its independent revision, including ABA protection. ACTIVE removal checks root revision and selection revision, even for non-default roots. A non-default removal submits null replacement; default removal submits a different ACTIVE replacement; the final ACTIVE Resume cannot be removed. The frontend must choose the next or otherwise previous item from its observed list and show the exact replacement in confirmation (WSP-011); the backend never chooses another one. Matching already-REMOVED no-op ignores present selection/replacement eligibility after syntax, receipt and target revision admission. Capacity is 100 ACTIVE Resumes and 1,000 ACTIVE Evidence Items.

## Editable values and examples

Profile's three nullable values are separate from Resume Header wording. Non-null full_name/phone_number/email use fixed Common outer trim, with bounds 100/50/254 code points respectively. Blank is invalid, not null. Phone syntax and bounded email syntax are defined in PRO-004/005; neither invokes a network check. Preserve case, internal spaces and Unicode form.

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "revision": 1,
  "full_name": "Ada",
  "phone_number": null,
  "email": "ada@example.test"
}
```

Evidence has six exact field shapes. `S` is nonblank trimmed single-line text, at most 200 code points. `?` means explicit null is permitted, not an optional key. Month is exactly ASCII YYYY-MM, year 0001–9999; no surrounding whitespace or moving future-date gate. Start must not exceed end when both exist; null end means ongoing, null event month unknown. URLs use the existing preserved-spelling HTTP(S) value rules and cause no fetch.

| kind | Complete fields |
| --- | --- |
| EDUCATION | school_name:S, degree, major:S?, start_month:Month?, end_month:Month? |
| WORK_EXPERIENCE | company_name:S, role_title:S, start_month:Month?, end_month:Month? |
| PROJECT | project_name:S, role_title:S?, project_url:HttpUrl?, start_month:Month?, end_month:Month? |
| SKILL | skill_name:S |
| AWARD | award_name:S, awarding_organization:S?, awarded_month:Month? |
| CERTIFICATION | certification_name:S, issuing_organization:S?, issued_month:Month? |

Candidate degree is one of SECONDARY_VOCATIONAL, HIGH_SCHOOL, ASSOCIATE, BACHELOR, MASTER, MBA, DOCTORATE. This is a separate unordered enum from Preferences education.

Evidence content is a plain ordered AST. Controls/line separators are rejected before trim. Text remains literal, including markup-looking characters and duplicates. Empty content is legal; empty blocks/list items are not. Bounds are 100 blocks, 100 items/list, 10,000 code points/paragraph or item, and 50,000 total text code points.

```json
{
  "request_id": "22222222-2222-4222-8222-222222222222",
  "kind": "SKILL",
  "fields": {"skill_name": "Python"},
  "content": [
    {"type": "PARAGRAPH", "text": "Maintained an internal reporting service."},
    {"type": "UNORDERED_LIST", "items": ["Implemented tests", "Reviewed changes"]}
  ]
}
```

Header optional kinds are JOB_SEARCH_STATUS, JOB_INTENTION, EXPECTED_POSITION, EXPECTED_CITY, EXPECTED_SALARY, HIGHEST_EDUCATION, GENDER, POLITICAL_AFFILIATION and YEARS_OF_EXPERIENCE. Each may occur once; array order is meaningful; values are S. This is wording, not saved facts. `sections: []`, `optional_items: []` and member `content: []` are legal. Included sections have nonempty members; kind and Item identity are unique within a document.

Local paragraph uses runs; ORDERED_LIST/UNORDERED_LIST uses `items: [{runs: [...]}]`. Each run has nonempty scalar text and explicit marks. Mark types are BOLD, ITALIC, UNDERLINE and LINK (LINK additionally requires url). No duplicate mark type is allowed. Raw validity precedes merging. Preserve run spaces; whitespace-only runs must be unmarked, and joined paragraph/item text must be nonblank. Marks canonicalize in that order and adjacent identical mark arrays merge, within one paragraph/item only. Segmentation/mark order differences alone do not publish. Body text limits match Evidence's counts, with at most 256 canonical runs/paragraph or item; a document admits 100 members and 200,000 local-text code points. Raw limits still apply before merge.

Fonts are SOURCE_HAN_SANS, HEITI, SONGTI and KAITI. font_size_pt is 12–20, line_spacing_pt is 14–30, both exact half-point numbers; line spacing must be at least font size + 2. Color is exactly # plus six hex digits, canonicalized uppercase, without trim. Use exact input number semantics; string/bool values or rounded fractional inputs are invalid. These are saved settings, not a supplied renderer or installed font asset guarantee.

## Errors, recovery and frontend handoff

ContractError is `{code, message, field_errors:[{field,code}]}`. Non-field-specific errors have an empty array. Paths use known names and submitted indices, for example `sections[0].members[0].evidence_item_version_id`. Unknown property names/values are never echoed; an unknown member key reports its nearest known parent. Do not parse message text for behavior.

| Status | Codes |
| --- | --- |
| 400 | BAD_REQUEST |
| 403 | ACCESS_DENIED |
| 404 | NOT_FOUND |
| 409 | REQUEST_CONFLICT, REVISION_CONFLICT, REVISION_EXHAUSTED, INVALID_STATE, SOURCE_CONFLICT, LAST_RESUME_REQUIRED, CAPACITY_EXCEEDED |
| 413 | REQUEST_TOO_LARGE |
| 422 | VALIDATION_ERROR; includes INVALID_REFERENCE for supplied missing/wrong-owner references and STRUCTURE_TOO_COMPLEX at `$` for raw node/depth budgets |
| 500 | INTERNAL_ERROR, including detected broken saved lineage |
| 503 | STORAGE_UNAVAILABLE (established non-commit for a write), OUTCOME_UNKNOWN |

Treat transport loss, OUTCOME_UNKNOWN and other 5xx without non-commit proof as pending verification. Preserve the exact original command and prevent replacement by different intent; explicit retry resends it unchanged. A later rejected retry does not prove the earlier attempt rolled back. Current equality is not proof of a request's outcome. Successful replay may contain old root/default/Baseline snapshots; fetch current separately. A failed read after confirmed success does not undo that success.

The existing frontend generator selects its supported interfaces; add this consumer explicitly when implementing it, and regenerate rather than hand-editing generated types. Shared error vocabulary and OpenAPI version have expanded; reconcile drift during that integration. M2 rendering/durable demand/export remains unavailable until its own scope is ready and implemented.
