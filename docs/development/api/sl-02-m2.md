## Operations

All six successful operations return HTTP 200.

| Method / path under `/api/v1` | Result |
| --- | --- |
| GET `/render-configurations` | `{ "items": [{ "configuration": {...}, "can_generate": true }] }`; only currently executable entries, ordered by ID |
| GET `/render-configurations/{render_configuration_id}` | Same single-entry envelope; retained configurations can have `can_generate: false` |
| POST `/render-intents` | Original acceptance snapshot, shown below |
| GET `/render-intents/{render_intent_id}` | Exact retained Intent state |
| GET `/artifacts/{artifact_id}` | Immutable metadata and contained exact-source manifest |
| GET `/artifacts/{artifact_id}/content` | Original verified PDF/PNG bytes; optional `disposition=inline` or `attachment` |

Choose a configuration from the available list; do not hardcode an implicit default or add `output_format` to the request. The current catalog includes PDF and PNG (1120 pixels wide per A4 page). Content equality across configuration IDs does not make IDs interchangeable.

```json
{
  "request_id": "10000000-0000-4000-8000-000000000000",
  "resume_version_id": "20000000-0000-4000-8000-000000000000",
  "render_configuration_id": "79264750-13c9-453a-ba57-41d23fe81243"
}
```

Use the actual saved ResumeVersion ID and a fresh client-generated UUIDv4 request ID. The configuration ID above is the shipped PDF configuration, not a fallback when listing fails. POST requires UTF-8 JSON, identity encoding and at most 4096 actual bytes. Only those three fields are accepted; duplicate JSON members are malformed. GET requests have no body or query except the single optional content disposition; duplicate disposition parameters fail even when equal.

```json
{
  "request_id": "10000000-0000-4000-8000-000000000000",
  "outcome": "ACCEPTED",
  "render_intent_id": "40000000-0000-4000-8000-000000000000"
}
```

Acceptance commits a retained request/Intent, not a promise that rendering succeeded. A verified prior artifact may fulfill immediately; otherwise demand joins one exact-pair unfinished Work or creates one. Work and attempt IDs are private. Save, current-version changes and merely reading a Resume do not create demand. New requests require an ACTIVE Resume and current configuration capability; accepted exact work and original receipt replay survive later removal/current-version changes.

## Polling, replay and content

Intent has exactly `render_intent_id`, `resume_version_id`, `render_configuration_id`, `status`, `created_at`, `finished_at`, `artifact_id`, `failure_code`.

| Status | Terminal fields |
| --- | --- |
| `PENDING` | `finished_at`, `artifact_id`, `failure_code` are null |
| `FULFILLED` | `finished_at` and `artifact_id` are present; `failure_code` null |
| `FAILED` | `finished_at` and `failure_code` are present; `artifact_id` null |

Terminal failure codes: `SOURCE_UNAVAILABLE`, `CONFIGURATION_UNAVAILABLE`, `PERMISSION_DENIED`, `RENDER_FAILED`, `OUTPUT_INVALID`, `RESOURCE_LIMIT_EXCEEDED`, `STORAGE_FAILED`, `RECOVERY_EXHAUSTED`, `INTERNAL_ERROR`. These are Intent results, separate from HTTP error codes.

Keep the original POST body until its result is known. After `OUTCOME_UNKNOWN` or transport loss, explicitly resend that same body/request ID. Replay returns the original ACCEPTED object even after fulfillment/failure, removal or payload loss; poll the Intent separately. Changing content under the same request ID yields `REQUEST_CONFLICT`. A new explicit generation after terminal failure uses a new request ID. Discard stale/out-of-order polling results under the Contract's client rules; those frontend obligations are not implemented by this backend task.

Artifact metadata has exactly `artifact_id`, `schema_version: 1`, `manifest`, `media_type`, `byte_length`, `sha256`, `created_at`. Its manifest contains schema version, exact Resume/root/Profile IDs, ordered section/kind/Evidence references, configuration ID and Artifact ID. Missing payload does not erase metadata or rewrite fulfillment.

Content sends the complete original bytes, including for a Range request (200, never 206), after length/SHA-256 verification into one stable snapshot. Headers include exact Content-Type/Content-Length, `Cache-Control: no-store` and `Content-Disposition: inline|attachment; filename="artifact-{artifact_id}.pdf|png"`. There is no gzip conversion, ETag or rerender-on-read. A failed download is separate from fulfillment. Browser preview/download behavior and client generation remain frontend integration work.

## Error handling

All failures use `{ "code": "...", "message": "...", "field_errors": [...] }`; known field errors contain only `field` and `code`. Do not interpret a successful configuration listing or metadata read as proof of source admissibility or byte availability.

| HTTP | Relevant error codes |
| --- | --- |
| 400 | `BAD_REQUEST` for invalid transport/JSON |
| 403 | `ACCESS_DENIED` |
| 404 | `NOT_FOUND` for an absent requested read identity |
| 409 | `REQUEST_CONFLICT`, `INVALID_STATE`, `RENDER_CONFIGURATION_UNAVAILABLE`; content-only `ARTIFACT_UNAVAILABLE` |
| 413 | `REQUEST_TOO_LARGE` |
| 422 | `VALIDATION_ERROR`, including new-request `INVALID_REFERENCE` for absent source/configuration |
| 500 | `INTERNAL_ERROR`; content length/hash mismatch `ARTIFACT_INTEGRITY_FAILED` |
| 503 | `STORAGE_UNAVAILABLE`, `OUTCOME_UNKNOWN` |

No public Work management, cancellation, retry/repair endpoint, configuration mutation, history list, MaterialBundle, model call or application fact exists. Backend and rendered-output tests are recorded in [traceability](../../progress/traceability.md#materials-backend-evidence); they do not establish frontend/browser acceptance.
