## 3. Source-backed implementation findings

The following official-source research was reviewed on 2026-09-19. It records source behavior and the intended mapping, not installed package compatibility or passed tests. SQLAlchemy's observed documentation release was 2.0.54, Alembic's 1.20.0, and the Python source was the 3.12 documentation branch. Pydantic v2, Zod and FastAPI source pages are rolling documentation; pin actual adopted releases and recheck the cited behavior at bootstrap.

| Source / studied scope | Fact and consequence for this consumer |
| --- | --- |
| [SQLAlchemy SQLite transaction control](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver) | Legacy sqlite3 transaction mode can execute DDL outside a real transaction. Choose one explicit driver transaction mode, rather than assume a context manager makes initialization atomic. |
| [Python 3.12 sqlite3](https://docs.python.org/3.12/library/sqlite3.html#transaction-control-via-the-autocommit-attribute) | With `autocommit=False`, a new transaction follows commit/rollback; `in_transaction=True` alone cannot identify the previous transaction's outcome. Configure connection PRAGMAs in a valid connection-setup phase, then verify actual settings. |
| [Alembic shared connection](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands), [SQLite dialect](https://alembic.sqlalchemy.org/en/latest/api/ddl.html#alembic.ddl.sqlite.SQLiteImpl.transactional_ddl), [autocommit blocks](https://alembic.sqlalchemy.org/en/latest/api/runtime.html#alembic.runtime.migration.MigrationContext.autocommit_block) | Share the explicit bootstrap Connection/transaction with Alembic and verify transactional DDL. An autocommit block can commit earlier work; do not use one inside atomic initialization. Include both application tables, application_id, user_version and Alembic metadata in fault-injection checks. |
| [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous), [transactions](https://www.sqlite.org/lang_transaction.html) | A conservative initial candidate is rollback DELETE journal with synchronous EXTRA; WAL+FULL is another option if actually justified. Read back configuration. Busy/error handling does not imply command replay or known rollback; Q42/STO-008 governs. These are implementation candidates, not a new Contract requirement to repeat COMMIT. |
| [Python fcntl](https://docs.python.org/3.12/library/fcntl.html#fcntl.flock) | Unix advisory locking can implement the current host's owner guard; it is not a Windows implementation. Bind lock identity to resolved physical placement, put lock resources outside data_directory, and test process death and dev-reloader behavior. |
| [Pydantic conversion](https://docs.pydantic.dev/latest/concepts/conversion_table/), [configuration](https://docs.pydantic.dev/latest/api/config/), [network types](https://docs.pydantic.dev/latest/api/networks/) | Default coercion/extra-field ignoring and HttpUrl's normalization/2083 limit differ from M1. Preserve raw admitted URL text and use parsing only for validation. Match COM-028's exact integral JSON value semantics: no string/bool/null coercion and no floating-point rounding of invalid input. Do not substitute StrictInt behavior blindly for the wire definition. Preserve exact numeric input through admission (for example, decimal-aware parsing before integrality/range checks); raw-request fixtures should admit `1.0`/`1e0` and reject `1.0000000000000001` rather than round it to 1. |
| [JSON Schema numeric types](https://json-schema.org/understanding-json-schema/reference/numeric#integer) | JSON Schema integer admits equivalent integral number spellings such as 1 and 1.0. OpenAPI, server admission and raw-request tests must agree with COM-028; malformed/nonintegral values stay invalid. |
| [Zod API](https://zod.dev/api), [JavaScript length](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/length) | Unknown fields may be stripped; URL convenience types can normalize or add domain-only rules. Current Zod documentation describes code-point length, whereas native JS string.length counts UTF-16 units. Verify the actual release instead of assuming all validators count the same way. |
| [FastAPI error handling](https://fastapi.tiangolo.com/tutorial/handling-errors/), [additional responses](https://fastapi.tiangolo.com/advanced/additional-responses/) | Default envelopes differ and raw validation errors can include input/body. Implement sanitized handlers and explicit OpenAPI error responses; do not serialize exceptions wholesale. |
| [TanStack mutations](https://tanstack.com/query/v5/docs/framework/react/guides/mutations), [network mode](https://tanstack.com/query/v5/docs/framework/react/guides/network-mode), [query defaults](https://tanstack.com/query/v5/docs/framework/react/guides/important-defaults) | Configure command retry/replay explicitly; no persisted mutation queue. Evaluate `networkMode: 'always'` for a loopback API so internet-offline status does not defer a command until later. Read refetch must not overwrite dirty forms or trigger navigation. Inspect generated transport too. |
| [Pinned URL Standard](https://url.spec.whatwg.org/commit-snapshots/8e14777cfa145b08a9fb735fe580ec0c366564c3/#url-writing) | Parse success alone does not establish validity; validation errors can accompany a URL result. MAE-004 pins validity independently of parser serialization. Server/client validators need one shared conformance fixture set. |
| [Window opening](https://developer.mozilla.org/en-US/docs/Web/API/Window/open), [opener](https://html.spec.whatwg.org/multipage/nav-history-apis.html#dom-opener), [referrer policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy) | Async resolution may outlive activation; noopener can make a successful open return null. Implement the accepted waiting-page protocol and final safety properties, then test real browsers. Do not mistake handle availability for page load/application success. |

## 4. Build and verify in bounded steps

1. **Bootstrap and startup:** build the minimum real backend/config/storage composition with failing checks for fresh/default/explicit paths, schema recognition, atomic initialization and runtime owner exclusion. Verify the chosen driver and lock behavior before business integration.
2. **Authority and API:** implement the two application tables, repositories/transactions, explicit create/update/delete/read/resolve use cases and sanitized HTTP adapters. Test receipt races, stale editors, no-op/max revision, physical deletion, restart and commit-response failures using actual SQLite.
3. **Frontend path:** implement the separate Job Pool entry view, whole-record forms, complete list, delete and waiting-page navigation using the generated client. Preserve unsaved input and distinguish known rejection from uncertainty; inspect actual request counts.
4. **Conformance and handoff:** execute [Acceptance 3.1](../../acceptance.md#31-sl-01m1-contract-conformance), record real requirement-to-test evidence, run the introduced lint/type/test/build checks, and update only the implemented milestone's evidence. Use generated fixture data, controlled HTTP destinations and temporary databases. No BOSS login, model call, real application or external form submission is needed for this milestone's verification. Standard E2E browser tests are distinct from a production recruiting-browser adapter.
