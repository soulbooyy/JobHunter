## 1. Authority and saved representation

<a id="pro-001"></a>
**PRO-001.** CandidateProfile MUST be the sole authority for the three v1 identity/contact values: full_name, phone_number and email. Career facts belong to [Evidence](evidence.md); collection intent to [Preferences](preferences.md); optional Header wording to [Resume](resumes-grounding.md). No nickname, GitHub, city, homepage, gender, political-affiliation or work-years field belongs to Profile. The single Profile MUST NOT be deleted in v1; clearing all three values is a valid Save. Contact fields MUST remain model-invisible by default; display support does not authorize model admission. (Q1/Q7/Q13; BC1/BC3.)

<a id="pro-002"></a>
**PRO-002.** The complete saved shapes MUST be:

| Object | Exact fields and types |
| --- | --- |
| CandidateProfile | profile_id: UuidV4; current_profile_version_id: UuidV4; revision: Revision; created_at: UtcTimestamp; updated_at: UtcTimestamp |
| ProfileVersion | profile_version_id: UuidV4; profile_id: UuidV4; schema_version: integer 1; full_name: string or null; phone_number: string or null; email: string or null; created_at: UtcTimestamp |

Business values MUST occur only in the immutable Version. The current pointer MUST reference a Version of that root. IDs, strict fields and metadata use COM-038; publication uses SAV-004/005. No Version revision, updated_at or is_current is introduced. (Q49/Q51/Q56.)

<a id="pro-003"></a>
**PRO-003.** Fresh S2-capable initialization and explicit migration MUST create exactly one real Profile root at revision 1 and a first immutable Version with all three values null, atomically under STO-022. Profile completeness MUST NOT gate Knowledge maintenance or Resume creation. An absent mandatory root/Version after initialization MUST NOT be repaired by an ordinary read or startup. Preferences remains lazy and no Resume is automatically created. (Q49/Q51/Q93.)

## 2. Contact values and equality

<a id="pro-004"></a>
**PRO-004.** All three contact keys MUST exist; each allows explicit null. Non-null input MUST use COM-025 scalar text and COM-026 fixed outer trim. A trimmed empty string MUST fail BLANK_VALUE, never become null. Preserve admitted internal spacing, case and Unicode form. full_name MUST contain 1–100 code points and no remaining controls or line/paragraph separators. phone_number MUST contain 1–50 code points, only ASCII digits, U+0020 spaces, hyphens, parentheses and at most one plus at the beginning, and at least one ASCII digit; other formats fail INVALID_FORMAT after shared scalar/character checks. No country inference, formatting repair or multiple-number structure is supported. (Q13/Q17.)

<a id="pro-005"></a>
**PRO-005.** A non-null email MUST contain 1–254 code points, exactly one @ with nonempty sides, and no remaining COM-026 whitespace/control characters or line/paragraph separators. This is bounded contact validation, not proof of deliverability or comprehensive email-standard conformance. Invalid syntax MUST fail INVALID_FORMAT; prohibited characters follow COM-039. Saving MUST NOT send email, check reachability, lowercase or repair it. Canonical Profile equality MUST compare the three admitted nullable strings exactly; object-key order and JSON spelling MUST NOT matter. (Q17/Q57/Q97.)

## 3. Exact use, reads and editing

<a id="pro-006"></a>
**PRO-006.** Resume Header MUST obtain the three fixed values from its exact profile_version_id, never duplicate them or override them privately. Populated values MUST display; null MUST produce no placeholder or label-only content. No presentation hide control is supported. Profile publication MUST NOT update any existing ResumeVersion. First/newly switched Resume reference MUST be current at commit; an unchanged exact reference from the preceding formal ResumeVersion MAY remain historical. Resume source admission is RES-011; command ordering is SAV-003. (Q14/Q59/Q60; BC3/A1.)

<a id="pro-007"></a>
**PRO-007.** The read interfaces MUST be GET /api/v1/profile → {profile: CandidateProfile, profile_version: ProfileVersion} and GET /api/v1/profile/versions/{profile_version_id} → ProfileVersion, both 200. The current pair MUST come from one consistent snapshot with matching root/current/owner IDs; exact reads MUST NOT substitute current content. Missing requested exact IDs use SAV-014; missing mandatory internal authority uses STO-028. No Profile-history listing/picker is introduced. Save accepts and returns only SAV-001/008 shapes. (Q75/Q78.)

<a id="pro-008"></a>
**PRO-008.** Profile edits MUST use the separate Profile Save. A Resume editor changing contact values MUST NOT treat unsaved values as a private saved Header; explicit Profile publication and explicit Resume source adoption are separate actions. Failed Save preserves the editing draft; no-op/replay/publication follow SAV-004–009. This Contract grants no automatic propagation or additional AI contact permission. (BC3/A1; Q14/Q57/Q60.)

## 5. CandidateProfileProjection schema v1 and paired publication

The 2026-09-24.S2M1S1-r2 amendment adds source_entry_id to each ProfileIndexEntry and INCREMENTAL generation provenance. Public Profile schema remains v1 for this development transition; model output is now grouped by Entry under PRO-013. Existing deterministic backend shapes must be adapted before semantic integration; this document does not claim the new wire shape is already served.

Scope revision **2026-09-24.S2M1S1-r1**. The [user-approved naming amendment](../../design/contract/sl-02-m1-supplement-grill.md#cg03s1-profile-entry-naming) names the collection entries and its element ProfileIndexEntry; the schema remains v1. Provenance: CG03S1-BC1–BC3 and effective Q6–Q41; Q24 is superseded by Q38/Q41.

<a id="pro-010"></a>
**PRO-010.** CandidateProfileProjection schema v1 MUST describe only supported capabilities observed from EVD-016’s default-source Evidence. User intent remains PreferenceSetVersion; no desired city/salary/role, contact/Header value, proficiency score, personality label or unsupported capability upgrade is allowed. Education, skills, experience domains and demonstrated directions use the same entry shape; no fixed category taxonomy is required.

<a id="pro-011"></a>
**PRO-011.** The immutable Profile MUST contain exactly schema_version: 1, resume_version_id, extraction_key and entries. entries is an ordered array of ProfileIndexEntry objects containing exactly source_entry_id: UuidV4, name: nonblank scalar string, description: nonblank scalar string and evidence_refs: nonempty array of EVD-018 EvidenceRef. Each source_entry_id MUST identify an Entry in the paired Evidence, and every ref in that ProfileIndexEntry MUST belong to that same Entry under PRO-017. name and description use Common scalar/control admission and retain admitted model text; finite output limits belong to the registered invocation configuration. Duplicate refs within one ProfileIndexEntry are invalid. No capability score or taxonomy is introduced. The identity and refs are derived source metadata, not user-editable facts.

<a id="pro-012"></a>
**PRO-012.** A portrait MUST publish Profile and Evidence as one coherent immutable pair: {portrait_id: UuidV4, schema_version: 1, resume_version_id, extraction_key, profile: CandidateProfileProjection, evidence: CandidateEvidenceProjection, generation: {kind: MODEL|INCREMENTAL|REUSE, run_id: UuidV4|null, reused_from_portrait_id: UuidV4|null}, created_at}. MODEL means all surviving Entry interpretations were regenerated: non-null run_id and null reused_from. INCREMENTAL means model-regenerated Entry groups combined with unaffected groups reused from one baseline: non-null run_id and reused_from. REUSE means a newly assembled pair needs no model call: null run_id and non-null reused_from. An unaffected Entry with an empty group still counts as a reused scope. The frozen build plan records actual regenerated/reused/deleted Entry identities and its baseline, including when no reused groups survive and kind is MODEL. Model kinds require the owning Invocation with a lawful complete durable response; publish/record the derivation decision under current qualification before confirming/ending that Run, never require it already ENDED. Exact historical reattachment under PRO-018 does not rewrite this immutable generation metadata. Source IDs/rules MUST match throughout. Only an eligible current build may attach the pair. READY requires nonempty merged entries with valid supported refs; an empty final Profile remains unavailable, never fabricated.

<a id="pro-013"></a>
**PRO-013.** Current-version model generation MUST use schema-constrained output over complete admitted current Evidence/background for exactly the Entry IDs selected by PRO-019. The output is exactly {entry_results:[{source_entry_id, entries:[{name,description,evidence_refs:[evidence_id,...]}]}]}. Each requested Entry MUST appear exactly once; an explicit entries:[] is valid for an Entry with no supported semantic result. Missing, duplicate or unrequested Entry groups are invalid, not implicit empty groups. Backend assigns each resulting ProfileIndexEntry its group source_entry_id and expands local IDs into exact EvidenceRefs against the frozen target projection. Every ref MUST resolve within that group's Entry. The model cannot select source version/rules or modify reused groups. Validate the complete response and complete assembled Profile under PRO-020. Any invalid group/entry, unsupported upgrade or invalid/cross-Entry ref rejects the whole build result; no silent pruning or partial publication. Structural validity cannot prove semantic support or completeness; required Eval covers that quality. No hidden second model judge is authorized.

<a id="pro-014"></a>
**PRO-014.** The current registered portrait consumer version MUST issue at most one Provider request per derivation attempt, containing all Entry groups requiring generation, and zero requests for proven reuse/deletion-only assembly or exact historical reattachment. This is the current implementation policy, not a permanent Domain limit: a future separately reviewed consumer version may introduce controlled batching without changing Entry-scoped semantics, after defining its budgets, atomic publication and recovery. Current code MUST NOT batch, truncate, silently split, repair, retry or fall back to another model. Capacity failure leaves this attempt unavailable. A complete durably stored response may recover local validation/merge/publication without redispatch; uncertain/incomplete dispatch remains failed/unavailable with truthful usage. Explicit refresh creates a new full-generation attempt after terminal failure under SAV-026. Missing required configuration, admission/budget denial or excessive protected input leaves portrait unavailable without blocking Resume Save. Reuse actual SL-03.M1/M2 admission, budget and durability; do not masquerade this consumer as safe render replay or the conformance exercise format.

The registered portrait consumer MUST also supply the EXR-024 whole-Run agreement before enabling real invocation. Its durable build outcome is either an exact validated pair (published current only under SAV-023), a deterministic terminal derivation rejection with its owned reason, or an obsolete-source disposition; none may be inferred merely from durable response bytes. A valid historical pair remains successful derivation without becoming current. A durably recorded complete derivation decision (including unusable/invalid Profile or proven admission denial with no remote uncertainty) establishes COMPLETION_CONFIRMED and may end COMPLETED under EXR-009; it does not imply READY. Fresh semantic-start rejection creates no Run. Actual remote uncertainty retains OUTCOME_UNKNOWN; actual time denial retains TIMED_OUT; authorized cancellation retains CANCELLED. Runtime-owned integrity/missing-handler failures retain their existing exact EXR causes. Do not promote generic HTTP failure, stale qualification or unconfirmed storage outcome into any terminal fact.

Registration MUST freeze a positive finite execution timeout and nonnegative finite local-recovery grace in the exact execution configuration. Establish the Run deadline at accepted semantic start, before any invocation; queued portrait waiting before that start does not authorize dispatch. Persist the local-recovery latest-grant instant as that deadline plus the frozen grace, with checked arithmetic; it cannot reset across restart. Admit only deterministic processing of a response durably available before the original deadline, using fresh current qualification, source/permission checks, SAV-023 fencing and a finite execution bound no later than that latest-grant instant. A complete recorded decision is confirmed before decoding/time admission. After the bound, genuinely unfinished work converges under EXR-011 without dispatch; already-ended Runs cannot reopen. Unknown commit/read outcome remains unresolved until owned bounded reconciliation establishes truth. This is a business consumer agreement, not the EVO conformance consumer or a universal recovery default; concrete finite values, adapter format keys and all registered configuration limits require executable adoption proof.

<a id="pro-015"></a>
**PRO-015.** CurrentPortraitState MUST contain exactly default_resume_selection, source_resume_version_id: UuidV4|null, status: NO_SOURCE|EMPTY_SOURCE|QUEUED|RUNNING|READY|FAILED, build_id: UuidV4|null, portrait_id: UuidV4|null and failure_code: string|null. NO_SOURCE has null source/build/portrait; EMPTY_SOURCE has source but null build/portrait. QUEUED/RUNNING has source/build and null portrait; READY has source/build/portrait and null failure; FAILED has source/build, null portrait and a sanitized code. Failures use SOURCE_UNAVAILABLE, CONFIGURATION_UNAVAILABLE, INPUT_NOT_ADMITTED, OUTPUT_INVALID, INVOCATION_FAILED or OUTCOME_UNKNOWN; no sensitive detail. failure_code MUST be non-null if and only if status=FAILED. This is mutable current publication state, not an immutable Profile field or claim that earlier history vanished. A coherent pair is visible as current only in READY.

<a id="pro-016"></a>
**PRO-016.** The user-portrait page MUST show source attribution, read-only supported capabilities and an edit-source route when ready. Otherwise show unavailable/source state and explicit refresh; no partial-Evidence browsing workflow. Refreshing a ready source makes new use unavailable immediately; failed refresh does not restore old-as-current. GET/page reload only observes. DeepFit clicked without ready portrait returns a clear unavailable prerequisite response with no hidden dispatch/fallback. Already-frozen analysis keeps exact historical inputs. Distinguish this from empty selected-Resume optimization, which checks only that selected document under RES-024.

## 6. Entry-scoped incremental generation

Scope revision **2026-09-24.S2M1S1-r2**. Provenance: [Entry amendment and Q42–Q46](../../design/contract/sl-02-m1-supplement-grill.md#cg03s1-entry-incremental). These requirements refine the prior generation/reuse policy without changing Resume authority or paired publication.

<a id="pro-017"></a>
**PRO-017.** Profile is an Entry-scoped semantic index. Every ProfileIndexEntry MUST belong to exactly one source_entry_id; all of its Entry-level or Block-level evidence_refs MUST have that parent Entry. Entry means any admitted Resume kind, including EDUCATION, WORK_EXPERIENCE, PROJECT, SKILL, AWARD and CERTIFICATION; structured-only Entries participate even without Blocks. Distinct Entries may independently yield the same capability label. Do not persist a global capability that merges their refs or recursively expand rebuilding through shared names/skills. Cross-Entry capability aggregation belongs to downstream DeepFit or another reviewed consumer at execution time. The current Resume schema has no admitted global career-fact field outside Entries; Header/contact/presentation changes do not create a global dirty scope.

<a id="pro-018"></a>
**PRO-018.** Automatic rebuild MUST select the latest successfully committed usable compatible portrait of the same Resume as its baseline, even if intervening source versions failed derivation. Determine latest by durable successful-derivation order, not UUID order or wall-clock comparison; reattaching an old portrait does not create a new derivation. Compatibility requires the current Entry-scoped output schema and the same immutable registered extraction, admission/privacy, prompt, model and output-validation semantics, with retained source/result integrity and actual access. Similar prose is not compatibility. Freeze that decision before execution. A failed/unpublished partial output or another Resume is never a baseline. No eligible baseline means full first generation; incompatible configuration likewise leaves no compatible baseline. The latest successfully committed compatible portrait for the same exact target ResumeVersion, using the same durable derivation order, may be reattached under the new current build/source fence with zero model calls. This exact-source lookup is distinct from the latest same-Resume baseline lookup; it MUST NOT select an older interpretation when a later successful compatible refresh of that same source exists. If source versions differ, even when admitted content is equal, the old portrait MUST NOT become current directly: derive target Evidence, diff/rebind and construct a new target-version pair. Baseline eligibility never grants currentness; current access, source, selection and build checks remain mandatory. Explicit full refresh does not take this automatic reuse path.

<a id="pro-019"></a>
**PRO-019.** For automatic incremental rebuilding, derive EVD-024's Entry diff against the frozen compatible baseline. Generate every added or changed surviving Entry as a whole, using its complete current admitted structured background and all original Evidence; do not send only changed bullets, prior Profile summaries, unchanged other Entries or deleted source text as replacement evidence. Reuse only proven unchanged Entries, preserving their supported name/description and rebinding every ref to the target exact version/rules. Removing an Entry removes its derived Profile group; it cannot dirty another Entry because cross-Entry refs are forbidden. A source with only removals and unchanged surviving Entries needs no model request. Reuse may include an empty group from a prior complete successful derivation. Full first generation and explicit refresh select all current Entries, with no reused groups. The selected scope is frozen before constructing the protected Frame; no hidden scope growth, shrinking or repeated call follows model output. An unavailable/corrupt required frozen source fails the build rather than guessing equality or silently choosing a different baseline.

<a id="pro-020"></a>
**PRO-020.** Assembly MUST completely replace each generated Entry's prior group, drop removed Entries, and combine validated regenerated groups with rebound unchanged groups exactly once. Serialize groups in target Evidence Entry order and preserve within-group model order or the baseline's within-group order. Global Entry reorder changes assembly order without dirtying an unchanged Entry. Do not merge/deduplicate across Entries because their labels match. An explicit empty generated group removes that Entry's prior Profile entries; missing response groups remain invalid under PRO-013. Validate the final full Profile against the target Evidence and provenance, not only model-created rows. Publish no partial Profile if any generated or reused part fails. If usable source remains but the merged Profile is empty, record unavailable OUTPUT_INVALID with the deterministic outcome, never restore deleted/stale capabilities; no-source/empty-source still uses PRO-015/SAV-021. Historical source/pairs/analysis refs stay unchanged. Entry-scoped omission does not prove that a capability is absent; EVD-021 continues to govern downstream assessment.
